# Анализ проекта MedicineAnalog и эпик MVP для диплома

## 1. Текущее состояние проекта

### 1.1 Назначение
**MedicineAnalog** — веб-приложение для поиска и сравнения лекарств из нескольких аптек Молдовы. Пользователь вводит название препарата и видит результаты по аптекам с ценами.

### 1.2 Архитектура
- **Backend:** Django 5.1
- **Данные:** Scrapy-пауки → JSON → management-команда `load2db` → SQLite
- **Аптеки:** AptekaMD, FarmacieMD, Farmacia Familiei, Hippocrates

### 1.3 Реализованный функционал
| Компонент | Описание |
|-----------|----------|
| **Модель** | `Medicine`: title, price, link, img, manufacturer, pharmacy, active_ingredient |
| **Поиск** | Главная страница: поиск по названию (`title__icontains`), группировка по аптеке, сортировка по цене |
| **Парсинг** | 4 паука Scrapy, выгрузка в JSON; поддержка manufacturer в части источников |
| **Загрузка в БД** | `load2db` с опциями `--pharmacy`, `--manufacturer` |
| **Очистка** | `clear_medicines` по аптеке |
| **Админка** | Регистрация Medicine, list_display, search, list_filter |
| **Вспомогательное** | `meds.description` — парсинг страницы товара apteka.md (жёсткие XPath); `meds.services` — OpenAI извлечение активного вещества (не интегрировано) |

### 1.4 Проблемы и пробелы
- **active_ingredient** в модели есть, но нигде не заполняется и не используется → нет поиска аналогов по действующему веществу.
- **Страница препарата** (`/medicine/<id>/`) возвращает `HttpResponse(medicine)` — нет нормальной карточки и описания.
- **Нет сценария "аналоги"** — главная ценность названия проекта не реализована.
- **API-ключ OpenAI** захардкожен в `services.py` — риски безопасности.
- **description.get_info** привязан к одному сайту и не встроен в просмотр препарата.
- Нет API, тестов, документации по архитектуре и сценариям использования.

## 2. Рекомендуемый функционал для MVP диплома

Цель: сделать **минимально жизнеспособный продукт**, который демонстрирует идею «поиск и сравнение лекарств и их аналогов» и достаточен для описания в дипломе (задачи, архитектура, реализация, выводы).

### 2.1 Ключевые направления

1. **Аналоги по активному веществу (ядро продукта)**  
   - Заполнение поля `active_ingredient` при загрузке/обновлении (например, через существующий `extract_active_substance` в `services.py` или правила/словарь).  
   - Раздел или фильтр «Показать аналоги»: группировка по `active_ingredient`, сравнение цен в разных аптеках.  
   - Это даёт чёткую постановку задачи и выводы для диплома.

2. **Нормальная страница препарата**  
   - Отдельный шаблон: название, производитель, активное вещество, цена, аптека, ссылка на аптеку, при возможности — описание (из `description.get_info` или краткое из БД).  
   - Исправить `view_description`: рендер шаблона вместо `HttpResponse(medicine)`.

3. **Сравнение цен**  
   - Для одного и того же препарата/аналога — таблица или карточки «в аптеке X — цена Y», «в аптеке Z — цена W».  
   - Можно реализовать на странице аналогов или на странице препарата (если есть записи из нескольких аптек с одним active_ingredient/title).

4. **Поиск по активному веществу**  
   - Опция в поиске: «по названию» / «по активному веществу» или единый поиск с подсказкой «найдены аналоги по веществу …».

5. **Безопасность и конфигурация**  
   - Вынести API ключ в переменные окружения (например, `OPENAI_API_KEY`) и использовать их в `services.py`.

6. **Обновление данных**  
   - Одна команда или скрипт, который по очереди запускает пауки и `load2db` (и при необходимости обновляет `active_ingredient`) — для актуальности данных и описания процесса в дипломе.

7. **Минимальная «научная» ценность для диплома**  
   - Краткое описание: источники данных, ограничения парсинга, способ определения активного вещества (правила vs ML/API), точность/ограничения.  
   - Этого достаточно для раздела «Практическая реализация» и выводов.

## 3. Эпик: MVP MedicineAnalog для дипломной работы

**Цель эпика:** довести проект до состояния «минимально жизнеспособный продукт» с акцентом на поиск и сравнение лекарств и аналогов, пригодный для описания в дипломе.

---

### Epic: MVP «Поиск лекарств и аналогов»

**Описание:**  
Реализовать полноценный сценарий поиска лекарств по названию и по активному веществу, отображение аналогов и сравнение цен в разных аптеках, а также страницу препарата и базовую инфраструктуру (безопасность, обновление данных).

**Критерии приёмки эпика:**  
- Пользователь может искать препараты по названию и видеть результаты по аптекам с ценами.  
- Для препаратов отображается активное вещество; пользователь может видеть аналоги (по активному веществу) и сравнение цен.  
- Есть отдельная страница препарата с основной информацией и ссылкой в аптеку.  
- API ключи не хранятся в коде.  
- Есть способ обновления данных из парсеров и загрузки в БД (одна команда/скрипт).  
- В репозитории есть краткое описание проекта и сценариев (README или docs).

---

#### Story 1: Заполнение и использование активного вещества
- **Как** разработчик/пользователь системы,  
- **я хочу,** чтобы у лекарств было заполнено поле «активное вещество» и чтобы по нему можно было искать и группировать аналоги,  
- **чтобы** реализовать сценарий «поиск аналогов по действующему веществу».

**Задачи:**  
- Заполнять `active_ingredient` при загрузке в БД (интеграция с `extract_active_substance` в `services.py` с возможностью отключения при отсутствии API ключа; или fallback по правилам/словарю).  
- В форме поиска или на странице результатов добавить возможность искать/фильтровать по активному веществу.  
- На странице результатов или отдельной странице показывать блок «Аналоги по действующему веществу» (группировка по `active_ingredient`, сравнение цен по аптекам).

**Приоритет:** высокий.

---

#### Story 2: Страница препарата
- **Как** пользователь,  
- **я хочу** открыть карточку препарата по ссылке с полной информацией и переходом в аптеку,  
- **чтобы** принять решение о покупке.

**Задачи:**  
- Реализовать view с рендером шаблона (не `HttpResponse(medicine)`).  
- Шаблон: название, производитель, активное вещество, цена, аптека, ссылка на сайт аптеки, изображение.  
- Опционально: подгрузка описания с сайта аптеки (например, через `description.get_info` для apteka.md) с обработкой ошибок и таймаутов.

**Приоритет:** высокий.

---

#### Story 3: Сравнение цен по аптекам
- **Как** пользователь,  
- **я хочу** видеть один и тот же препарат (или аналоги) с ценами в разных аптеках в одном месте,  
- **чтобы** выбрать наиболее выгодный вариант.

**Задачи:**  
- На странице аналогов или на странице препарата выводить таблицу/карточки: аптека — цена — ссылка.  
- Учесть случай одного препарата в нескольких аптеках и группы аналогов по активному веществу.

**Приоритет:** высокий.

---

#### Story 4: Безопасность и конфигурация
- **Как** разработчик,  
- **я хочу** не хранить API ключи в коде,  
- **чтобы** проект был безопасным и готовым к выкладке в репозиторий.

**Задачи:**  
- Вынести OpenAI API ключ в переменную окружения (например, `OPENAI_API_KEY`).  
- В `services.py` брать ключ из `os.environ` / `django.conf.settings`; при отсутствии ключа — логировать предупреждение и не вызывать API (fallback для `active_ingredient`: пусто или правило).

**Приоритет:** средний.

---

#### Story 5: Обновление данных из парсеров
- **Как** администратор/разработчик,  
- **я хочу** одной командой или скриптом обновить данные по всем аптекам (запуск пауков + загрузка в БД),  
- **чтобы** поддерживать актуальность каталога для диплома и демо.

**Задачи:**  
- Добавить management-команду или shell-скрипт: по очереди запуск Scrapy по каждому источнику и вызов `load2db` с нужными аргументами.  
- В readme/docs описать шаги обновления данных.

**Приоритет:** средний.

---

#### Story 6: Документация и описание для диплома
- **Как** автор диплома,  
- **я хочу** иметь краткое описание проекта, сценариев и ограничений,  
- **чтобы** использовать это в постановке задачи и выводах.

**Задачи:**  
- README: назначение проекта, как запустить (виртуальное окружение, миграции, статика, опционально — Scrapy и load2db).  
- Краткий раздел в docs или README: источники данных, способ определения активного вещества, ограничения (сайты, частота обновления, точность аналогов).

**Приоритет:** средний.

---

### 4. Ограничение объёма (чтобы остаться в MVP)

- **Не в scope MVP:** сложная авторизация, личные кабинеты, мобильное приложение, рекомендации, полноценный REST API для внешних клиентов.  
- **В scope:** описанные выше 6 историй; при нехватке времени приоритет: Story 1 → 2 → 3 → 4 → 5 → 6.

---

### 5. Итог

Текущий проект уже даёт парсинг нескольких аптек, загрузку в БД и простой поиск по названию. Для **минимально жизнеспособного продукта для диплома** достаточно добавить:  
- использование **активного вещества** (заполнение + поиск аналогов + сравнение цен),  
- **нормальную страницу препарата**,  
- **безопасную конфигурацию**,  
- **одну команду обновления данных** и  
- **краткую документацию**.  

Эпик выше структурирует это в виде историй и задач, которые можно брать в бэклог и оценивать по срокам диплома.
